# Fingerprinting surface

What Turnstile and Cloudflare bot-management actually measure, and where each signal is
collected. Claims are tagged: **[confirmed by source]** (a fetched citation supports it),
**[observed]** (seen in our own live capture), **(inferred)** (reasoning, not directly sourced).

Cloudflare's own framing: Turnstile runs "a series of small non-interactive JavaScript challenges
to gather signals about the visitor or browser environment," including "proof-of-work
(computational puzzles), proof-of-space, probing for web APIs, and various other challenges for
detecting browser-quirks and human behavior." **[confirmed by source: https://developers.cloudflare.com/turnstile/]**
The GA blog is blunter: "the actual act of checking a box isn't important, it's the background data
we're analyzing while the box is checked that matters," collected by "running a series of in-browser
tests, checking browser characteristics, native browser APIs" plus "proof-of-work tests,
proof-of-space tests." **[confirmed by source: https://blog.cloudflare.com/turnstile-ga/]**

So the JS side is a signal-collection harness, not a puzzle. The signals below are what such a
harness can read, cross-checked against the specific host-API references our capture found in the
versioned loader bundle (`isTrusted`, `Function.prototype.toString` + error `stack`, `mousemove` +
`touchstart`, `navigator.platform`).

## 1. Behavioral / interaction

| Signal | Source layer | Note |
|---|---|---|
| `Event.isTrusted` | JS (loader) | separates real input from synthetic dispatch |
| `mousemove`, `touchstart` listeners | JS (loader) | interaction presence + entropy |
| timing / dwell before solve | JS + server | uniform timing reads as automation |

`Event.isTrusted` is `true` only "when the event was generated by the user agent (including via user
actions and programmatic methods such as `HTMLElement.focus()`)," and `false` "when the event was
dispatched via `EventTarget.dispatchEvent()`." **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted]**
That single boolean defeats the naive `element.dispatchEvent(new MouseEvent('click'))` automation
path, because scripted events carry `isTrusted === false`. Our capture confirms `isTrusted`,
`mousemove`, and `touchstart` are referenced directly in the loader bundle **[observed]** — the
minifier can't rename host-API property names, so they survive as plaintext.

Scrapfly's writeup states the behavioral layer keys on timing regularity: "Human users exhibit
variable delays and natural browsing sequences; automated scrapers typically demonstrate perfectly
uniform timing patterns." **[confirmed by source: https://scrapfly.io/blog/posts/how-to-bypass-cloudflare-anti-scraping]**
Actual mouse-path entropy scoring in the runtime payload is (inferred) — not in the loader layer we
captured.

## 2. Automation tells

| Tell | What exposes it | Source |
|---|---|---|
| `navigator.webdriver === true` | `--enable-automation`, `--headless`, `--remote-debugging-port 0` | [confirmed](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/webdriver) |
| `window.chrome` missing | headless Chrome | [confirmed](https://intoli.com/blog/not-possible-to-block-chrome-headless/) |
| permissions inconsistency | `Notification.permission === 'denied'` while query state is `prompt` | [confirmed](https://intoli.com/blog/not-possible-to-block-chrome-headless/) |
| `navigator.plugins.length === 0`, empty `languages` | headless Chrome | [confirmed](https://intoli.com/blog/not-possible-to-block-chrome-headless/) |
| `HeadlessChrome` in UA | old headless default | [confirmed](https://intoli.com/blog/not-possible-to-block-chrome-headless/) |
| `cdc_`/CDP driver globals | ChromeDriver injection | [confirmed](https://github.com/ultrafunkamsterdam/undetected-chromedriver) |
| function-hook detection | `Function.prototype.toString`, error `stack` | [observed] + [confirmed](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Function/toString) |

`navigator.webdriver` "indicates whether the user agent is controlled by automation," and in Chrome
is `true` under `--enable-automation`, `--headless`, or `--remote-debugging-port 0`. **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/webdriver]**
The intoli teardown enumerates the classic headless leaks: `window.chrome` absent, the
`Notification.permission`/`navigator.permissions` contradiction, `navigator.plugins.length === 0`,
empty `navigator.languages`, and `HeadlessChrome` in the UA. **[confirmed by source: https://intoli.com/blog/not-possible-to-block-chrome-headless/]**
undetected-chromedriver targets exactly this surface — it patches the ChromeDriver-injected
variables (the `cdc_`-prefixed globals / CDP artifacts) but "instead of removing and renaming
variables, we just keep them, but prevent them from being injected in the first place," and claims
to pass "Distil / Imperva / DataDome / CloudFlare IUAM." **[confirmed by source: https://github.com/ultrafunkamsterdam/undetected-chromedriver]**
(The exact `$cdc_asdjflasutopfhvcZLmcfl_` global-array naming is well documented in RE tooling but
not quoted in the source above — treat the specific string as (well-known, not re-verified here).)

Function-hook detection is the interesting one, because it directly counters the bypasses above.
Any built-in function's source, via `Function.prototype.toString`, is a native function string of
the form `function abs() { [native code] }`; a user-defined replacement returns "the source text
segment which was used to define the function." **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Function/toString]**
So if an anti-detect tool redefines `navigator.webdriver`'s getter or wraps `WebGLRenderingContext.
getParameter`, calling `.toString()` on the hook reveals JS source instead of `[native code]`.
Our capture found both `Function.prototype.toString` and error `stack` referenced in the loader
bundle **[observed]** — the `stack` read is consistent with throwing inside a probed call and
inspecting the stack frame to see whether a Proxy or wrapper sits in the call chain. CreepJS
formalizes this whole category as "Detect and ignore JavaScript tampering (prototype lies)" and
"Fingerprint lie patterns." **[confirmed by source: https://github.com/abrahamjuliot/creepjs]**
This is why "just spoof `navigator.webdriver`" fails: the spoof itself is a detectable tell.

## 3. Canvas / WebGL

Canvas fingerprinting draws text/shapes to a `<canvas>`, then reads pixels back (via `toDataURL()`
or `getImageData`) and hashes them; the same draw yields different pixels per device because of
"Anti-aliasing, hinting, and font availability... depending on your operating system, hardware, and
settings" and "Differences in GPU or graphics drivers." **[confirmed by source: https://fingerprint.com/blog/canvas-fingerprinting/]**
WebGL adds a hardware identifier: the `WEBGL_debug_renderer_info` extension "exposes two constants
with information about the graphics driver," `UNMASKED_VENDOR_WEBGL` ("Vendor string of the graphics
driver") and `UNMASKED_RENDERER_WEBGL` ("Renderer string of the graphics driver"). **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/WEBGL_debug_renderer_info]**
A headless GPU stack (SwiftShader / llvmpipe) or a spoofed renderer string that doesn't match the
rest of the profile is a strong tell. **(inferred)** These heavier vectors were **not** in the
loader bundle we captured **[observed]** — consistent with Cloudflare deploying canvas/WebGL/audio
probes only in the runtime challenge-platform payload, which a `3x000…` test sitekey does not fully
serve.

## 4. Audio

`OfflineAudioContext` fingerprinting routes an `OscillatorNode` through a `DynamicsCompressorNode`,
renders offline, and hashes the samples (e.g. summing absolute values). The output varies by
"Floating-point arithmetic precision," "Platform-specific optimizations (different FFT
implementations on macOS versus other systems)," and browser-engine differences, while staying
stable within one environment. **[confirmed by source: https://fingerprint.com/blog/audio-fingerprinting/]**
Same collection layer as canvas/WebGL — runtime payload, not the loader. **(inferred)**

## 5. Device / navigator consistency

The scoring here is less about any single value and more about whether values agree with each other
and with the HTTP headers.

| Signal | API | Fingerprint role |
|---|---|---|
| logical CPUs | `navigator.hardwareConcurrency` | "number of logical processors available to run threads" [confirmed](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/hardwareConcurrency) |
| RAM bucket | `navigator.deviceMemory` | power-of-2 GiB, clamped (e.g. 2/4/8/16/32) [confirmed](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory) |
| platform / UA | `navigator.platform`, `navigator.userAgentData` | cross-check vs UA string |
| languages, screen, DPR, fonts, `maxTouchPoints` | various | entropy + coherence |

`navigator.deviceMemory` is deliberately coarse — "rounding the actual memory to the nearest power
of 2, then dividing... clamped within lower and upper bounds," e.g. one of `2, 4, 8, 16, 32`
**[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory]** —
so it's a coherence check, not an identifier. `navigator.platform` appears directly in our loader
bundle **[observed]**. The User-Agent Client Hints API (`navigator.userAgentData` with `brands`,
`mobile`, `platform`, and gated `getHighEntropyValues()`) gives a second, structured source for
platform/version that must agree with the legacy UA string and with `navigator.platform`. **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/User-Agent_Client_Hints_API]**
A UA claiming Windows Chrome while `platform` says `Linux` or UA-CH says something else is the kind
of contradiction the lie-detection layer flags. **(inferred, see CreepJS "Resistance (Known
Patterns)": [confirmed](https://github.com/abrahamjuliot/creepjs))**

## 6. Network layer (server-side, pairs with the JS)

This is why "works on my desktop, fails headless on a datacenter IP" — the JS can be perfect and the
transport still betrays you.

**TLS / JA3 / JA4.** JA3 hashes the ClientHello fields
`SSLVersion,Cipher,SSLExtension,EllipticCurve,EllipticCurvePointFormat` with MD5. **[confirmed by source: https://lwthiker.com/networks/2022/06/17/tls-fingerprinting.html]**
Because "each client uses a different TLS library" (Chrome BoringSSL, Firefox NSS, Python OpenSSL),
the fingerprint differs sharply — Python offers ~43 cipher suites vs Chrome's ~16 — and controlling
it from a scripting language is hard: "the underlying TLS library may not send the exact list you
specified." **[confirmed: same source]** Cloudflare computes JA3/JA4 "during the TLS (SSL)
handshake," and JA4 "improves upon JA3 by sorting ClientHello extensions, which reduces fingerprint
variations among modern browsers" (i.e. it's resilient to Chrome's extension-order randomization);
rules can "block an incoming threat" or "allow the JA3 seen across good requests." **[confirmed by source: https://developers.cloudflare.com/bots/concepts/ja3-ja4-fingerprint/]**

**HTTP/2.** The Akamai-style H2 fingerprint combines the SETTINGS frame values ("Firefox
consistently sends one set of parameter, Chrome another"), the WINDOW_UPDATE increment, PRIORITY
frames, and pseudo-header order (`:method`, `:authority`, `:scheme`, `:path`) into
`S[;]|WU|P[,]#|PS[,]`. **[confirmed by source: https://www.trickster.dev/post/understanding-http2-fingerprinting/]**
A common tell: "many scripts still use HTTP1.1... a clear signal to Cloudflare." **[confirmed by source: https://scrapfly.io/blog/posts/how-to-bypass-cloudflare-anti-scraping]**

**IP reputation / ASN.** Cloudflare buckets IPs by origin — residential and mobile carry "high
trust," while datacenter IPs (AWS, Google Cloud) "have low trust and are often blocked." **[confirmed by source: https://scrapfly.io/blog/posts/how-to-bypass-cloudflare-anti-scraping]**
These transport signals feed the same scoring: the bot-management ML engine assigns a 1–99 score
from "request features (headers, session characteristics, and browser signals)," alongside a
heuristics engine and an optional JS-detections engine that "identifies headless browsers and other
malicious fingerprints." **[confirmed by source: https://developers.cloudflare.com/bots/concepts/bot-score/]**

## 7. Packaging and the token

Flow (from our capture): loader → versioned bundle → POST to
`…/cdn-cgi/challenge-platform/h/b/turnstile/f/av0/rch/<seg>/<sitekey>` **[observed]**. The bundle
assembles the collected signals plus proof-of-work/proof-of-space output **[confirmed by source: https://blog.cloudflare.com/turnstile-ga/]**
and posts them to that challenge-platform endpoint; the exact payload schema is the gated,
byte-level part and is not reproduced here. The result is the `cf-turnstile-response` token, which
the site's backend validates by POSTing `secret` + `response` (+ optional `remoteip`) to
`https://challenges.cloudflare.com/turnstile/v0/siteverify`; the JSON reply carries `success`,
`challenge_ts`, `hostname`, `action`, `cdata`, and `error-codes` (e.g. `timeout-or-duplicate` for a
reused token). **[confirmed by source: https://developers.cloudflare.com/turnstile/get-started/server-side-validation/]**
The token is single-use and short-lived, so replaying a captured token fails at siteverify. **[confirmed: same source]**

---

## What this doc is / isn't

**Is:** a sourced map of the fingerprinting *surface* — which signals exist, where each is collected
(loader JS vs runtime payload vs transport), and citations you can re-verify. The section-2 and
section-6 pairing explains the recurring "desktop passes, headless-on-datacenter fails" outcome.

**Isn't:** a byte-level deobfuscation of the versioned bundle, the challenge-platform payload schema,
or the token construction — those stay in the gated teardown. It is not a token-forgery method:
tokens are single-use and server-validated, so nothing here bypasses siteverify. Vectors labeled
**(inferred)** or tied to the runtime payload were reasoned or seen indirectly, not confirmed in the
loader we captured with a test sitekey.
