# Behavioral / interaction fingerprinting (Turnstile loader)

How Turnstile detects *human interaction* in the versioned loader bundle: trusted events,
mouse/touch/key listeners, and timing/stack telemetry. Claims tagged **[confirmed by source]**
(fetched citation), **[observed]** (our live capture of the `/turnstile/v0/b/<hash>/api.js` ~84 KB
bundle), **(inferred)** (reasoning). Variable names below are the bundle's own mangled identifiers;
host-API names (`isTrusted`, `addEventListener`, `Error().stack`) can't be minifier-renamed, so the
interaction logic stays legible.

## The core: `isTrusted` as the gate

Every interaction signal in this layer is gated on `Event.isTrusted`. From the capture **[observed]**:

```js
var c=function(s){s.isTrusted&&(U.add(i),t(i))};
window.addEventListener("keydown",c,!0);
window.addEventListener("mousemove",c,!0);
window.addEventListener("touchstart",c,!0);
```

`c` runs its body — `U.add(i)` (record the interaction into a set) and `t(i)` (fire the callback) —
**only** when `s.isTrusted` is truthy. That single boolean is the whole defense against synthetic
input: `isTrusted` is `true` "when the event was generated by the user agent (including via user
actions and programmatic methods such as `HTMLElement.focus()`)," and `false` "when the event was
dispatched via `EventTarget.dispatchEvent()`"; even `HTMLElement.click()` "sets the `isTrusted`
property to `false`." **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted]**
So the naive automation path — `el.dispatchEvent(new MouseEvent('mousemove'))` or `el.click()` —
registers `isTrusted === false` and the listener body never executes. The interaction is silently
dropped, not rejected; there's no error to catch **(inferred)**.

The `!0` third argument to `addEventListener` is `true` = **capture phase**: the listener fires
"before being dispatched to any `EventTarget` beneath it in the DOM tree," ahead of the target and
bubbling phases. **[confirmed by source: https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener]**
Registering on `window` in capture means Turnstile sees the event before any page handler can
`stopPropagation()` it — you can't starve the widget of interaction events by intercepting them
downstream **(inferred)**.

The same trusted-only gate guards the postMessage channel (widget iframe ↔ host) **[observed]**:

```js
function Ko(e){return e.isTrusted&&zo(e.data)}
```

A `MessageEvent` forged via `dispatchEvent` fails `e.isTrusted`; only a real `postMessage`-delivered
event (which the UA marks trusted) reaches the `zo(e.data)` payload validator.

## Which events, and what they signal

| Listener | Capture phase | What it evidences |
|---|---|---|
| `keydown` | yes (`!0`) | keyboard presence + inter-key timing |
| `mousemove` | yes | pointer path, cadence, presence |
| `touchstart` | yes | touch device, coarse pointer |
| postMessage (`Ko`) | n/a | trusted cross-frame handshake |

Registering all three of keydown/mousemove/touchstart covers desktop *and* touch input from one gate.
The set `U` deduplicates (`U.add(i)`) so the signal is "did a trusted interaction of kind *i* occur,"
i.e. presence/entropy, not a raw event count **(inferred from `Set.add` semantics + [observed] code)**.

## Timing and stack telemetry

Interaction presence pairs with a timing/stack probe **[observed]**:

```js
function ji(e,t){try{var r=new Error().stack; ... [e, Math.max(0,Math.floor(X()-t)), r, ...]
```

`Math.max(0,Math.floor(X()-t))` is a non-negative integer delta (elapsed time since a reference `t`,
`X()` being the clock) — a dwell/latency measurement bundled with a tag `e` and the call stack `r`.
The `new Error().stack` read is dual-purpose: it timestamps *and* exposes whether a Proxy or wrapper
sits in the call chain of a probed API **(inferred)** — a hook-detection tie-in to the native-function
check `ma(e){return Function.toString.call(e).indexOf("[native code]")!==-1}` in the same bundle
**[observed]**.

Why timing matters: the behavioral layer keys on regularity. Scrapfly's teardown of Cloudflare's
detection notes it checks "Are there mouse moves and pauses?", advises injecting "random timeouts
(2 to 5 seconds)" and to "Mimic mouse moves and keyboard input," and states the score "drops" on
robotic request cadence because "Real users don't do that."
**[confirmed by source: https://scrapfly.io/blog/posts/how-to-bypass-cloudflare-anti-scraping]**
Uniform deltas from a scripted solve are a tell; the `ji` delta is the raw material for that scoring.

## Bypass implications

| Automation approach | Result at this layer |
|---|---|
| `dispatchEvent` / synthetic `MouseEvent` | dropped — `isTrusted === false` |
| `HTMLElement.click()` | dropped — sets `isTrusted` false **[confirmed: MDN]** |
| CDP `Input.dispatchMouseEvent` / real driver input | trusted — UA-generated, passes the gate (inferred) |
| downstream `stopPropagation()` | ineffective — capture-phase listener on `window` fires first |
| uniform/zero-dwell solve | passes `isTrusted` but feeds robotic timing into `ji` scoring |

The practical takeaway: clearing this layer needs input that the *browser itself* originates (driver-
level or real user), plus human-like timing — patching `isTrusted` to `true` is itself a
`Function.toString` tampering tell caught by `ma()` **(inferred)**.

## Not in this layer

Mouse-path *shape* scoring (curvature, jerk, Fitts-law plausibility), canvas/WebGL/audio, and the
final payload schema are **not** in the loader — they load in the runtime challenge-platform payload
a `3x000…` test sitekey doesn't fully serve **[observed]**. Treat path-scoring specifics as
(inferred), not confirmed here.
